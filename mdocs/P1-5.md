## 2. 任务详情

### Epic P1.5-A：播放链路

#### P1.5-1 播放队列持久化（App 重启后恢复）

- **依赖**：无　**规模**：M
- **描述**：当前播放队列（`usePlaybackStore.queueItems` + `queueMode` + 当前播放集）仅存内存，App 重启后丢失。需在重启后恢复队列结构与当前播放位置（不自动出声）。
  - **存储方案定案**：主进程 SQLite 新增 `playback_queue` 表（与 `episodes` 的引用一致性、可随数据导入导出，比 electron-store 更符合 Local-first 数据域定义）。
  - 主进程新增 `queue` 域：`saveQueue(episodeIds[], mode, currentEpisodeId)` / `loadQueue(): {episodeIds, mode, currentEpisodeId} | null`，写入时机为队列变更（addToQueue / playEpisode / setQueueMode / 集数播放完成）时 debounce 落库。
  - 渲染进程启动恢复流程：AppShell 在 `getLastSession()` 恢复单集播放后，再 `loadQueue()` → 按 episodeId 查 episodes 表还原 `Episode` 对象 → 设置 `queueItems`/`queueMode`。队列中已删除/已退订的集数自动剔除。
  - 需新增 `drizzle/0004_queue.sql` 迁移 + 迁移测试；`data-portability` 导出/导入需包含队列（导出 JSON 增 `queue` 字段，向后兼容）。
- **验收标准**：
  - Given 队列有 [A, B, C] 且当前播放 B、模式为随机，When 重启 App，Then 队列仍为 [A, B, C]、模式为随机、当前集恢复为 B 且不自动播放。
  - Given 队列中的某集被取消订阅删除，When 重启恢复，Then 该集从队列剔除，其余保留。
- **测试要求**：集成测试（QueueRepository 读写 + 迁移 0004 + 导出/导入含队列）；渲染端单测（恢复逻辑、脏集过滤，用 mock IPC）。
- **交付物**：`src/main/features/queue/queue.repository.ts`（表 + IPC `queue:{save,load}`）、`drizzle/0004_queue.sql`、`ipc-contract.ts` 扩展、AppShell 恢复接线、`data-portability` 增补、PlaybackStore 队列变更时触发 save。

#### P1.5-2 集数描述时间戳跳转

- **依赖**：无　**规模**：S
- **描述**：集数详情 `EpisodeDetailPanel` 中 `episode.descriptionHtml` 渲染的富文本里，`mm:ss` / `h:mm:ss` 形式的时间戳文本改为可点击，点击后跳转播放进度到对应秒。基于当前播放集为同一集时生效；非当前集则先播放该集再跳转。
  - **实现要点**：主进程 `sanitizeRichHtml` 清洗后仍保留时间戳文本；渲染端在 `dangerouslySetInnerHTML` 之外，用轻量后处理——把纯文本/HTML 节点中的 `(?:(\d+):)?(\d{1,2}):(\d{2})` 匹配替换为 `<button data-ts>`，点击调 `usePlaybackStore.seek()`（同集）或 `playEpisode(episode, podcast, {fromSec})`（异集）。注意 XSS：只对清洗后的 `descriptionHtml` 操作，时间戳按钮不插入 HTML 属性值，用事件委托。
  - 跳转前校验目标秒数 ≤ 时长（无时长时允许）。
- **验收标准**：
  - Given 某集描述含 `12:34` 且正在播放该集，When 点击，Then 进度跳到 754s。
  - Given 点击时间戳时播放的是另一集，When 点击，Then 切到该集并从 754s 播放。
- **测试要求**：纯函数单测（时间戳正则提取 + 越界钳制）；组件测试（点击事件→store 调用）。
- **交付物**：`lib/timestamp-link.ts`（提取/替换纯函数 + 测试）、`EpisodeDetailPanel.tsx` 事件委托接线。

#### P1.5-3 章节时间轴（`podcast:chapters` / PSC）

- **依赖**：无　**规模**：L
- **描述**：解析 Feed 的 `podcast:chapters`（`<psc:chapters>` 与 `<podcast:chapters>` 两种命名空间，格式均为 JSON，`chapters[]` 含 `startTime`/`title`）或 `<podcast:chapter>` 元素，存入 episodes 表，集数详情展示可点击章节列表。
  - **范围控制（关键）**：先做**可行性评估**——抽样 5~10 个真实 Feed 检查章节标签覆盖率（rss-parser `customFields` 支持 `podcast:chapters` 需手动配置 namespaces）。若覆盖率过低（如 <10%），按 §8 建议降级为「解析 + 存储 + 仅在元数据存在时展示」，UI 空态不突兀。
  - 数据模型：`episodes` 增 `chaptersJson text` 列（迁移 0005）；`Episode` 类型增 `chapters?: Chapter[]`。
  - 集数详情页章节区：点击章节标题跳转播放到 `startTime`（复用 P1.5-2 的 seek 逻辑）。
- **验收标准**：
  - Given Feed 提供 `podcast:chapters`，When 解析并打开集数详情，Then 展示章节列表，点击跳转到对应时间。
  - Given Feed 无章节，When 打开详情，Then 不渲染章节区（无空占位）。
- **测试要求**：feed-parser 单测（两种命名空间解析 + 格式容错）；组件测试（章节列表渲染与跳转）；迁移测试。
- **交付物**：feed-parser 章节解析、`chaptersJson` 列迁移、章节组件、跳转接线。

#### P1.5-7 播放失败自动重试与分类处理

- **依赖**：P1.5-1（队列上下文，切集重试需回到队列）　**规模**：M
- **描述**：播放失败（`audio` 的 `error` 事件）当前仅置 `playbackError` 文案。需分类处理：
  - **文件丢失**：本地文件被删/损坏 → 走 `verifyLocal` 检出后提示「文件已丢失，请重新下载」，提供下载按钮（已有 `fileMissing` 路径，补齐按钮与状态）。
  - **网络中断/源不可用**（在线播放 4xx/5xx/连接失败）→ 提示「网络错误」，提供「重试」按钮（重新 `playEpisode`）；自动重试 1 次（间隔 2s）后仍失败才停下，避免无限重试。
  - **解码失败**（`MEDIA_ERR_SRC_NOT_SUPPORTED`/`MEDIA_ERR_DECODE`）→ 提示「无法解码该音频」，不自动重试。
  - 错误类型判定基于 `audio.error.code`（1=abort, 2=network, 3=decode, 4=src_not_supported）+ `navigator.onLine`。
- **验收标准**：
  - Given 在线播放时网络中断，When 音频报 network 错误，Then 自动重试 1 次，仍失败则显示「网络错误 + 重试」按钮。
  - Given 播放本地已下载文件但文件已被外部删除，When 播放，Then 提示「文件丢失，重新下载」并提供下载入口。
  - Given 音频解码失败，When 报 decode 错误，Then 直接提示不可播放，不重试。
- **测试要求**：store 单测（mock audio.error 分类 → 状态转换）；组件测试（重试/重新下载按钮）。
- **交付物**：`store.ts` 错误分类 + 重试逻辑、`EpisodeDetailPanel`/播放器错误区按钮、i18n 文案。

### Epic P1.5-B：下载链路

#### P1.5-4 整栏播客 / 播放列表批量下载

- **依赖**：无（复用 `downloadService.enqueue`）　**规模**：M
- **描述**：新增两个批量下载入口，均进入现有统一下载队列（并发数由队列控制）：
  - **播客详情页「下载全部」**：将该播客未下载的集数全部入队（分页遍历 `listByPodcastPage`，避免一次性拉全量）。
  - **播放列表「批量下载」**：将播放列表内未下载的集数全部入队。
  - 批量入队返回 `{ enqueued, skipped }`（skipped = 已下载/已在队列）；队列并发限制在 `DownloadQueue` 已实现，无需改动调度。
  - 主进程提供 `download:enqueueMany(episodeIds[])` 批量方法（事务内逐条 `enqueue`，单条失败不阻塞其余），避免渲染层循环调用 IPC。
- **验收标准**：
  - Given 某播客有 10 集未下载，When 点击「下载全部」，Then 10 个任务进入队列，下载面板显示 10 条。
  - Given 播放列表含 5 集且其中 2 集已下载，When 批量下载，Then 仅 3 集入队，提示 `{ enqueued: 3, skipped: 2 }`。
- **测试要求**：集成测试（批量入队 + 去重 + 单条失败容错）；E2E（详情页下载全部 → 队列增长）。
- **交付物**：`download.service.enqueueMany()`、`download:enqueue-many` IPC、详情页/播放列表页按钮 + 结果提示。

#### P1.5-5 存储空间不足预警

- **依赖**：P1.5-4（下载前统一检查）　**规模**：S
- **描述**：下载入队前检查磁盘剩余空间（`statfs` 类调用：主进程用 `fs.statfs` / Node 22+ 或 `check-disk-space` 轻量依赖），低于阈值（默认 500MB，可配置）时：
  - 入队时提示「磁盘空间不足（剩余 X GB），已暂停新增下载」，任务仍入队但标记 `paused`，待空间释放后手动继续；或直接拒绝并提供「清理旧下载」跳转（`cleanup.service` 已有预览）。
  - 下载过程中实时占用增长接近耗尽时发出预警通知（可关闭）。
  - **定案**：入队时检查 + 拒绝（最简单可靠），不做运行中动态预警。设置页「存储」区展示剩余空间 + 阈值项。
- **验收标准**：
  - Given 磁盘剩余 < 阈值，When 尝试下载，Then 拒绝并提示剩余空间与清理入口，不产生任务。
  - Given 磁盘空间充足，When 下载，Then 正常入队。
- **测试要求**：主进程单测（阈值判定，mock `statfs`）；设置页组件测试（阈值展示）。
- **交付物**：`storage.service` 增 `checkFreeSpace()` + `freeSpaceThresholdMB` 设置项、`download.service` 入队检查、设置页展示。

#### P1.5-8 下载质量设置（评估 → 建议 → 决定）

- **依赖**：无　**规模**：S（调研）+ 视结论
- **描述**：PRD §6.4 P1「若 Feed 提供多码率/多格式选项，允许用户选择」。**先评估**：
  - 事实核查：播客 RSS 主流标准（RSS 2.0 + iTunes 命名空间）**只支持单一 `<enclosure>`**，多码率需 feed 提供多个 enclosure 或自定义命名空间（极少数）。当前 `feed-parser` 仅取首个 `enclosure.url`。
  - 可行性：多数播客源（Apple Podcasts 生态）不提供多码率；提供者需自定义解析，覆盖度预计 <5%。
  - **建议**：P1.5 不做完整质量选择 UI；仅（可选）把 feed 中如存在的多个 enclosure 按优先级（`type`/`length`）选择最合适的一个存入音频 URL，作为「多格式兜底」。产出评估结论后更新 Feature.md 勾选状态与备注。
- **验收标准**：
  - 产出评估文档（见 §8），明确「做 / 不做 / 降级方案」结论并更新 Feature.md。
  - 若选择实现多 enclosure 兜底：Given feed 提供多个 enclosure，When 解析，Then 按优先级选取并标注所选质量。
- **测试要求**：评估本身无需测试；若实现兜底，feed-parser 单测（多 enclosure 选取）。
- **交付物**：`mdocs/Download-Quality-Evaluation.md`（评估结论）、Feature.md 更新、（可选）feed-parser 多 enclosure 选取。

### Epic P1.5-C：数据可靠性

#### P1.5-6 数据库健康检查与损坏自愈

- **依赖**：无　**规模**：S
- **描述**：启动时（`migrateDatabase()` 之前或之后）对数据库做完整性校验：
  - **校验方式**：better-sqlite3 `PRAGMA integrity_check`（全量扫描，数据量大时耗时；可先做 `PRAGMA quick_check`，失败再全量）。
  - **自愈策略**：quick_check 失败 → 尝试从最近迁移备份（`migrate.ts` 已生成 `.bak-*`）恢复；无可用备份 → 将损坏库改名保留（`.corrupt-<ts>`），以全新库启动，并在 UI 提示「数据已损坏，已从备份恢复 / 无法恢复，请从数据导出文件重新导入」。
  - 入口：`infra/db/client.ts` 的 `getSqlite()` 打开后执行校验；日志记录校验结果（复用 `infra/logger`）。
  - **注意**：不与迁移回滚冲突——迁移失败已回滚并抛错；启动自愈是另一层（打开即损坏的情况）。
- **验收标准**：
  - Given 数据库文件被外部程序破坏，When 启动，Then 不崩溃退出；有备份则恢复并提示，无备份则保留损坏文件并以空库启动 + 明确提示。
  - Given 数据库完好，When 启动，Then 校验通过，无额外提示，启动时间不显著增加（quick_check 单次 < 300ms）。
- **测试要求**：主进程集成测试（构造损坏文件 → 断言恢复/空库 + 提示）；`quick_check` 性能打点。
- **交付物**：`infra/db/health.ts`（校验 + 恢复 + 提示 IPC）、启动接线、i18n 文案。

## 3. P1.5 完成的定义（Definition of Done）

1. 本文档全部 8 项完成（P1.5-8 以评估结论交付）；每个功能项验收标准有对应自动化测试或明确人工验收记录；
2. CI（lint → boundaries → typecheck → test → coverage → build → E2E）全绿；
3. 覆盖率：新增核心域（queue / storage-free-space / db-health）语句覆盖率 ≥ 85%，全局不低于当前 90.22%；
4. `Feature.md` 对应条目更新为 `[x]` 或补充备注（含 P1.5-8 评估结论）；
5. `data-portability` 导出/导入兼容队列新字段（旧备份文件仍可导入，新字段缺失时按空队列处理）；
6. 发布 `v2.1.0`（P1.5 完成后），走已验证 release 流程。
