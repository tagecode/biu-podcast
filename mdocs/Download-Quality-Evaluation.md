# 下载质量设置（多码率）可行性评估

| 字段     | 内容                                                                        |
| -------- | --------------------------------------------------------------------------- |
| 关联任务 | P1.5-8（PRD §6.4 P1「若 Feed 提供多码率/多格式选项，允许用户选择」）        |
| 结论     | **P1.5 不做完整的质量选择 UI**；仅保留「多 enclosure 兜底选取」，覆盖度低   |
| 日期     | 2026-08-09                                                                  |

---

## 1. 事实核查：播客 RSS 的多码率现状

播客订阅使用 RSS 2.0 + iTunes 命名空间（`<itunes:*>`）。主流规范对音频文件的描述**只支持一个 `<enclosure>`**：

- Apple Podcasts 官方规范：每个 `<item>` 一个 `<enclosure>`，提供 `url` / `type` / `length`。
- 多码率分发在播客生态中**没有广泛采用的标准**：
  - 少数厂商（如某些托管平台）会为同一集放**多个 `<enclosure>`**，但无统一顺序/质量标记约定；
  - 更常见的是不同**码率的独立 Feed**（如 64k / 128k 两个订阅源），由用户自己选订阅哪个，而非客户端内切换；
  - 自定义命名空间（如 `podcast:alternateEnclosure`）是提案性质，未被主流托管/客户端采用。

当前 `feed-parser.ts`（`src/main/features/subscription/feed-parser.ts`）的行为：`pickAudioUrl` 取第一个 `<enclosure>` 的 `url`，忽略其余。这与绝大多数客户端（Apple Podcasts、小宇宙、Overcast）一致——**它们也都取第一个 enclosure**。

## 2. 覆盖度估计

| 场景 | 预期占比 | 说明 |
| ---- | -------- | ---- |
| 单一 enclosure（标准） | ~95%+ | Apple Podcasts 生态、主流自托管 |
| 多 enclosure 但同码率（镜像/CDN） | <5% | 多个地址指向同一音频，无质量差异 |
| 多 enclosure 且多码率 | <1% | 极少，且无统一标记，客户端只能猜 |

结论：**为 <1% 的 Feed 构建完整 UI（质量选择器、记忆偏好、重新下载流程）ROI 极低**，且没有可靠的「标准/高/原声」映射规则。

## 3. 建议

### 做（P1.5 落地）
多 `<enclosure>` 兜底选取：当 Feed 提供多个 enclosure 时，按稳定优先级挑一个**最合适**的存入 `audioUrl`，不做用户可感知的选择 UI：

1. 优先 `audio/mp3`、`audio/mpeg`（最通用的容器）；
2. 其次按 `length` 最大的（通常为原声质量）；
3. 否则取第一个（与现状一致）。

改动范围：`feed-parser.ts` 的 `pickAudioUrl` + 单测。**不新增设置项、不新增 IPC、不涉及下载逻辑。**

### 不做（明确排除）
- 设置页「下载质量（标准/高/原声）」选择器；
- 已下载文件的质量重下/替换；
- 按播客记忆质量偏好。

### 后续（P2 或放弃）
若未来接入公开目录 API 或发现某托管平台普及了多码率约定，再重新评估。PRD §6.4 该条的验收口径可改为「多 enclosure 时选择最合适的源」，而非用户选择质量。
